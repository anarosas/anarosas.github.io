_Note: This article assumes you are using Ruby 3.3.1, Rails 7.1, Docker desktop 4.30.0_

On my quest to getting back to development, and also passing some interviews, I decided to venture a little more with Docker.

I have used Docker in some projects, but there was always someone else who had set it up, and I would barely need to make changes to it.

While working on a personal project I took the opportunity to go a bit further and setup my development and production environments with Docker.

After some trial and error, like using different Dockerfiles from boilerplates, I decided to rollback and stick to the Dockerfile generated by Rails 7.1 when you create your app.

But there’s a catch. This file is written for production by default. So I had to do some tweaks when defining the ENV variables.

```yaml
# Set ~production~ development environment
ENV RAILS_ENV="development" \ #change production for development
    BUNDLE_DEPLOYMENT="1" \
    BUNDLE_PATH="/usr/local/bundle"
# BUNDLE_WITHOUT="development" -> comment or remove this; otherwise your development gems won't be installed
```

Since my project uses Tailwind I added the build command on the Dockerfile as well. And that was it, not many changes were needed for the development. For this development environment I created a file `Dockerfile.dev` to separate from the production one, that will have different needs.

To build the image using this specific file, you can run:

`docker build -f Dockerfile.dev -t your_app_dev .`

So now you have the image of your app, but you will still need a service for you database, and since it’s your development environment you will still need the volume of your app to point to the local directory where you have all your code and files. This way when you add gems, or run a command that generates files, they will be created on your local directory and you will be able to commit them ✨

To manage and run your services you will need a `docker-compose.yml` A minimal version for an development app could be something like this:

```yaml
services:
  your_app_dev:
    build: .
    container_name: your_app_development
    volumes:
      - ./:/rails # points to your local directory so you can make changes  there
    command: bash -c "rm -f tmp/pids/server.pid && bin/rails s -p 3000 -b '0.0.0.0'"
    ports:
      - "3000:3000"
    env_file:
      - .env
    depends_on:
      db:
        condition: service_healthy
  db:
    image: postgres:16
    ports:
      - "5432:5432"

    environment:
      POSTGRES_USER: "${POSTGRES_USER}"
      POSTGRES_PASSWORD: "${POSTGRES_PASSWORD}"
    volumes:
      - pg_data:/var/lib/postgresql/data
    healthcheck:
      test: pg_isready -U "${POSTGRES_USER}"
      interval: 2s
      timeout: 5s
      retries: 30

volumes:
  pg_data:
```

You will need an .env file to set your ENV keys, such as POSTGRES_USER and POSTGRES_PASSWORD. Also note that you need to add a host on your database.yml config file. The host name should be the same as the name of your database service on the docker-compose.yml file, in this case db. It’s important to mention that you’ll also need a volume for your database service, this volume it’s what will make your data be persistant (and don’t be destroy at every build)

Your container will have it’s own network namespace, meaning that if you want to access your running rails server you need to make it accessible outside that network. Docker compose handles this via the ports directive. In this example I’m using 3000:3000 meaning that connections to port 3000 on the host machine will be redirected to port 3000 inside the container. However there’s a catch, by default rails in development environment will only listen on [localhost](http://localhost) (127.0.0.1 or ::1), so the redirection won’t work. To solve this, we need to add `0.0.0.0` to bind the server to all interfaces, instead of only using [`localhost`](http://localhost) and its `lo` interface.

To run your service you only need to run:

`docker compose up`

To run your migrations you can run

`docker exec your_app_web-1 bin/rails db:setup`

where `your_app_web-1` is the name of the web service container. You can retrieve this with `docker ps`

With this setup you can now run something like:

`docker compose run --rm your_app_dev bin/rails g rspec:install`

And have your generated rspec files in your local directory, ready to be worked on and committed.

You should now have your local development environment ready. If you are using VSCode you could also probably use [Dev containers](https://code.visualstudio.com/docs/devcontainers/containers#_create-a-devcontainerjson-file). The setup we just went through, allows you to work with whatever text editor / IDE you prefer, while also having more control (and understanding) on what’s happening in your containers.
